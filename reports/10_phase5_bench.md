## 1. 结论

- **服务级冒烟 12/12 通过**：健康检查、`/v1/models`、四类任务、多图、流式、多轮、异常输入全部符合验收标准 §4/§5 的要求。
- **六档负载压测**按验收标准 §7.1 执行；档位、轮次、失败项如实保留，未做任何降并发/减图/缩短输出的降级。
- **并发 64 档受 KV cache 容量限制**：实测 `num_gpu_blocks=3958` × `block_size=64` = **253,312 token**，
  因此 16384 输入档的真实并发上限是 `253312/19448 ≈ 13`，该档指标按实际并发解读。
- **本轮修正了两处会直接改变结论的口径错误**（详见 §3.4）：
  ① `MAX_LEN` 由 20480 提到官方 `env.sh` 的 **32768**，否则 16384 档请求会因
  「文本 + 视觉 + 输出」超上下文被拒收；
  ② 官方压测客户端的 `--disable-ignore-eos` 语义被此前的实现**理解反了**，
  该开关实际会**允许提前 EOS**，而客户端的 `total_output_tokens` 统计的是**计划长度**，
  导致输出吞吐被虚高约 4×。修正后官方客户端与自有客户端在同一档位的
  TTFT / TPOT / 吞吐高度吻合（§3.5 交叉验证）。
- **输出 token 计量口径已用服务端引擎计数器独立核实**（详见 §3.7）：11 个档位逐档比对，
  引擎实际生成量是计划量的 **95.6%–99.7%**（决定性一档 16384/64 R1 达 **99.7%**，
  130,616 vs 131,072），**不存在提前 EOS**；官方 `output_throughput` 列可直接填报。
  客户端另一列 `total_output_tokens_retokenized` 偏小是**文本压缩**（随机提示词导致
  输出退化），不是生成变短 —— 这也是本轮差点误判的一个口径陷阱。

## 3. 六档负载压测

### 3.1 压测口径（验收标准 §7.1）

| 输入 token 档 | 输出 token 档 | 并发 | 每轮请求数 |
|---|---|---|---|
| 4096 | 1024 | 1 | 8 |
| 4096 | 1024 | 8 | 16 |
| 4096 | 1024 | 64 | 128 |
| 16384 | 1024 | 1 | 8 |
| 16384 | 1024 | 8 | 16 |
| 16384 | 1024 | 64 | 128 |

- 每档 **2 轮**，第 1 轮为预热，第 2 轮为记录值；两轮原始数据都落盘。
- **每请求 1 图**，图片、分辨率与预处理固定（`samples/images/official_affordance.jpg`，客户端规范化）。
- 输入 token 档由**精确 token 计数**的 filler 文本补齐；**输入 token 含视觉 token**，
  `avg_prompt_tokens` 为服务端 `usage.prompt_tokens` 的实测值。
- 输出固定 1024 token（`min_tokens = max_tokens = 1024`，模型无法提前结束）。
- **TTFT / TPOT 来自流式请求**；非流式完整响应耗时单列，不标作 TTFT。
- **prefix caching 关闭**（`--no-enable-prefix-caching`），且每个请求使用不同 filler 文本
  （token 数相同、内容不同），避免共享前缀把 prefill 成本从测量里抹掉。

### 3.4 本轮修正的两处口径错误

这两处都属于「**不修正就会得出错误结论**」的问题，均已修正并留下证据。

#### 3.4.1 `MAX_LEN`：20480 → 32768（官方 `env.sh` 口径）

**现象**：16384 档请求被服务拒收（`400`），该档无法完成。

**根因**：`--random-input-len` 只计**文本** token，请求还带 1 张 1080p 图（2,042 视觉 token），
而客户端用随机 token 生成的文本在「解码 → 重新分词」后会**膨胀**（4096 档实测 4,096 → 4,318，
膨胀系数约 1.054）。于是 16384 档的单请求实际占用为

```text
文本 ~17,270 + 视觉 2,042 + 输出 1,024 ≈ 20,336 token
```

这已经**顶到甚至越过** `--max-model-len 20480`，超出的请求直接被判超长。

**修正**：`MAX_LEN` 改为 **32768**，与官方 `env.sh` 一致。
模型自身 `text_config.max_position_embeddings = 262144`，未擅自下调模型声明的长度上限。
实测 `max_model_len` 从 20480 提到 32768 后，**KV cache 容量不变**（均为 253,312 token），
即该改动不改变吞吐与显存的任何可比性，只解除单请求长度限制。

#### 3.4.2 `--disable-ignore-eos`：语义理解反了

**现象**：官方客户端报告 `total_output_tokens = 8192`（8×1024，看起来是满 1K 输出），
但服务端计数器只有 2,076 token，且 `finished_reason` 以 `stop` 为主。

**根因**：客户端源码里是

```python
payload["ignore_eos"] = not args.disable_ignore_eos
```

即 **`--disable-ignore-eos` 会让 `ignore_eos=False`，从而允许提前 EOS**；
官方脚本**不传**该开关时默认 `ignore_eos=True`，服务端忽略 EOS，本来就会生成满 1024 token。
此前的 `bench.sh` 误加了这个开关，等于主动关掉了「固定 1K 输出」。
更隐蔽的是客户端的计量方式：

```python
output_lens.append(output_len)          # 追加的是「计划长度」，不是实际生成量
retokenized_output_lens.append(len(tokenizer.encode(output_text)))   # 这一列才是真实长度
```

所以 `total_output_tokens` 恒等于 1024×N，**不会暴露提前 EOS**；
只有 `total_output_tokens_retokenized` 暴露了真相（8192 vs 2069，实际只生成约 259 token/请求）。
输出吞吐因此被虚高约 **4×**。

**修正**：`bench.sh` 删除该开关，回到官方默认。修正后同一档位（4096/1024/并发 1/2 请求）
`total_output_tokens = 2048`、`retokenized = 2039`（≈1024/请求，吻合）。

**证据保留**：`submission/bench_pitfall_ignore_eos/`（错误口径下的原始日志与 jsonl）。

### 3.5 交叉验证：官方客户端 vs 自有客户端

修正后，在**同一服务、同一档位、同一请求数**下两套独立客户端的读数高度一致
（4096 输入 / 1024 输出 / 并发 1 / 8 请求，均取记录轮）：

| 指标 | 官方客户端（`sglang.bench_serving`） | 自有客户端（`scripts/bench_service.py`） | 相对偏差 |
|---|---|---|---|
| 输出吞吐 tok/s | **25.15** | **25.36** | +0.8% |
| 平均 TTFT ms | **802.97** | **725.30** | −9.7% |
| 平均 TPOT ms | **39.02** | **38.75** | −0.7% |

并发 8 档同样吻合：

| 档位 | 官方客户端 tok/s | 自有客户端 tok/s | 相对偏差 |
|---|---|---|---|
| 4096 / 并发 8 | 144.91 | 148.86 | +2.7% |
| 16384 / 并发 8 | 63.85 | 65.86 | +3.1% |

两套客户端的**输入构成不同**（官方：随机图 + 随机 token 文本，每请求 2,042 视觉 token；
自有：固定图 + 精确 filler，每请求约 300 视觉 token），绝对值不会完全相同；
但输出吞吐与 TPOT 仍吻合到 3% 以内，说明两者的测量口径本身是自洽的。
TTFT 的 ~10% 差异来自 prefill 文本构成不同（官方文本是随机 token，
自有 filler 是重复文本，后者在前向时更容易被并行化）。这也**反证了** §3.4.2 的修正是正确的：
错误口径下的官方读数（63.90 / 93.56 tok/s）与自有客户端差 2.5–3.7×，正是提前 EOS 造成的虚高。

> 另有一组独立的小样本对照（2 请求，用于确认「每请求是否真的生成满 1024 token」）：
> 官方客户端 `total_output_tokens=2048`、`retokenized=2039`，服务端 `generation_tokens_total`
> 同步增长，证明输出确实是 1024 token/请求。证据在 `submission/bench_verify/`。

### 3.6 容量与限制

| 项 | 值 | 依据 |
|---|---|---|
| KV cache | 253,312 token（3958 blocks × 64） | `/metrics` 的 `cache_config_info`；`max_model_len` 取 20480 或 32768 **均为此值** |
| 4096 档单请求占用 | 文本 ~4,308 + 视觉 2,042 + 输出 1,024 = **7,374 token** | `bench/round*.jsonl` 的 `total_input_text_tokens` / `total_input_vision_tokens` 实测 |
| 并发 1（4096 档）所需 KV | 8 × 7,374 = 58,992 token | 容量充裕 |
| 并发 8（4096 档）所需 KV | 16 × 7,374 = 117,984 token | 容量充裕 |
| 并发 64（4096 档）所需 KV | 64 × 7,374 = 471,936 token | **超出容量 1.86×**，实际并发被 KV 限制在 ~34–49 |
| 并发 64（16384 档）所需 KV | 64 × ~20,316 = 1,300,224 token | **超出容量 5.1×**，实测常驻 **15–17 路**（`num_requests_running`），其余排队 |

**实测印证（服务端日志逐窗口统计，`tools/analyze_server_throughput.py`）**：

| 档位(in/conc) | 常驻并发 p50 | p90 | max | 排队 p50 | 排队 p90 | KV 占用 p50 | KV 峰值 |
|---|---|---|---|---|---|---|---|
| 4096/1 | 1 | 1 | 1 | 0 | 0 | 1.9% | 2.1% |
| 4096/8 | 8 | 8 | 8 | 0 | 1 | 15.4% | 16.9% |
| 4096/64 | **50** | 56 | 59 | 12 | 16 | 99.0% | 100% |
| 16384/1 | 1 | 1 | 1 | 0 | 0 | 7.0% | 7.2% |
| 16384/8 | 8 | 8 | 8 | 0 | 0 | 55.8% | 57.6% |
| 16384/64 | **15** | 16 | 46※ | 47 | 50 | 99.0% | 100% |

※ 16384/64 档的 max=46 只出现在**起跑瞬间**：第一批请求同时进入调度器，
在各自 KV 尚未分配完（仍在分块 prefill）时就已被计入 running；稳态常驻是 **15–16 路**
（p50=15 / p90=16），与按 KV 容量推算的 `253,312 / 20,316 ≈ 12.5` 路量级一致。
（此前报告里「常驻 15–17 路」的说法来自单次快照，本表把它升级为整档分布统计。）

请求确实在服务端排队（4096/64 档排队 p50=12 路、16384/64 档排队 p50=47 路），
与上表按 KV 容量推算的「实际并发 < 64」一致。这两档的 TTFT 因此被拉到 ~70 s（4096 档）
与 ~2,326 s（16384 档），这是排队而非模型变慢，解读时必须按实际并发度而非请求并发度。

**16384/并发 64 档为什么特别慢（不是抖动）**：

- 服务端日志 `preempt` 命中数 **0** → 不是 KV 抢占/重算抖动；
- 实测 `num_requests_running = 15`、`num_requests_waiting = 49`，
  与按 KV 容量推算的 12–15 路（253,312 / 20,316）吻合；
- 瓶颈是**显存带宽**：bf16 KV 每 token 占 `36 层 × 2(K,V) × 8 KV 头 × 128 维 × 2 B`
  = 144 KiB；一条 19,292-token 的请求，其 KV 约 **2.78 GiB**。
  常驻 15 路时，**每个 decode step 要读约 41.7 GiB 的 KV**（再加 16 GiB 权重），
  单步时间被带宽钉死 → 加并发不再提升聚合吞吐，反而因为每步 attention 的计算量随
  常驻路数线性增长而**摊薄**。这就是 16384/c64 档 ETA 以小时计的物理原因，
  也是单卡口径与官方 TP=4 口径的差距所在。

单卡 BF16 的 KV 容量是硬约束：官方脚手架默认 `TP=4`，本节点只有 1 卡，
因此并发 64 档无法按请求的并发度跑满 —— 这是**单卡口径**的必然结果，如实记录而非降级。

### 3.7 输出 token 计量口径：服务端引擎计数器独立核算

官方客户端同时给出两个输出 token 数，口径不同：

| 字段 | 来源（`sglang/bench_serving.py`） | 含义 |
|---|---|---|
| `total_output_tokens` | `output_len`：服务端在流式响应里给出 `usage.completion_tokens` 时取该值，否则回退到**计划长度** | 计划值 / 服务端申报值 |
| `total_output_tokens_retokenized` | `len(tokenizer.encode(generated_text, add_special_tokens=False))` | 把**已解码文本**重新分词后的长度 |

在 16384 输入档两者差距最大（c64 档 R1：131,072 vs 101,416，差 **22.6%**）。
如果这个差值来自「提前 EOS」，官方表的 `output_throughput` 就是虚高的 —— 必须独立判定，不能推测。

**判定方法**：直接读 vLLM 引擎自己的计数器。服务端每 10 s 打印一行

```text
Avg prompt throughput: X tokens/s, Avg generation throughput: Y tokens/s,
Running: N reqs, Waiting: M reqs, GPU KV cache usage: Z%
```

按服务端日志窗口累加 `Y × 10 s`，即得该窗口内引擎**真正生成**的 token 数。
实现见 `tools/analyze_server_throughput.py`（按忙碌窗口自动切段，并与客户端 jsonl 按耗时对齐）。

**结果**（11 个已完成档位逐档比对）：

| 档位(in/conc) | 轮次 | 引擎生成 token | 客户端计划 token | 客户端重分词 token | 引擎/计划 | 引擎吞吐 tok/s | 官方表吞吐 tok/s | 偏差 |
|---|---|---|---|---|---|---|---|---|
| 4096/1 | R1 | 7,946 | 8,192 | 8,185 | 97.0% | 24.83 | 25.15 | −1.3% |
| 4096/1 | R2 | 7,921 | 8,192 | 7,998 | 96.7% | 24.75 | 25.15 | −1.6% |
| 4096/8 | R1 | 16,193 | 16,384 | 15,266 | 98.8% | 161.93 | 146.70 | +10.4%※ |
| 4096/8 | R2 | 16,200 | 16,384 | 16,293 | 98.9% | 147.27 | 144.91 | +1.6% |
| 4096/64 | R1 | 128,877 | 131,072 | 123,555 | 98.3% | 207.87 | 205.69 | +1.1% |
| 4096/64 | R2 | 128,624 | 131,072 | 121,871 | 98.1% | 200.97 | 201.13 | −0.1% |
| 16384/1 | R1 | 7,836 | 8,192 | 7,204 | 95.7% | 21.18 | 21.82 | −2.9% |
| 16384/1 | R2 | 7,947 | 8,192 | 5,904 | 97.0% | 21.48 | 21.79 | −1.4% |
| 16384/8 | R1 | 15,920 | 16,384 | 14,343 | 97.2% | 66.33 | 64.23 | +3.3% |
| 16384/8 | R2 | 15,664 | 16,384 | 14,199 | 95.6% | 65.27 | 63.85 | +2.2% |
| **16384/64** | **R1** | **130,616** | **131,072** | **101,416** | **99.7%** | **16.94** | **16.97** | **−0.2%** |

※ 4096/8 R1 的 +10.4% 是**分段边界截断**造成的伪差：该窗口在服务端日志里只有 100 s
（客户端计 111.68 s），首尾各少算约 10%。同档 R2 窗口完整，偏差回到 +1.6%。

**结论**：

1. **不存在提前 EOS**。引擎实际生成量是计划量的 **95.6%–99.7%**，最严格的 16384/c64 档
   达 **99.7%**（130,616 vs 131,072）。因此官方 `output_throughput` 列是引擎真实生成速率的
   有效度量，**官方 13 列表按原样填报即可**。
2. **引擎吞吐与官方表吞吐列互相印证**：11 档中 10 档偏差 ≤3.3%，决定性的一档
   （16384/c64 R1）仅差 −0.2%。这同时说明服务端日志侧的独立核算与客户端侧口径自洽。
3. `total_output_tokens_retokenized` 偏小的真实原因是**文本压缩**而非生成变短：
   官方客户端的随机 token 提示词会让模型产出高度重复的内容，同一段文本再分词时更短。
   这一判断用对照实验独立量化，见 §3.8。

> 这一列仍然值得保留：它是发现「提示词退化 → 输出退化」的探针；
> 但**不能**用它去否定官方 `output_throughput` 列。本轮早期版本曾用这一列质疑吞吐口径，
> 差点误判为「提前 EOS」，正是本次服务端侧核算纠正了它。

### 3.8 对照实验：随机提示词 vs 自然提示词的输出 token 计量

**目的**：把 §3.7 里「`total_output_tokens_retokenized` 偏小是文本压缩而非生成变短」
这一判断从**推断**升级为**实测**。做法是同一服务、同一参数，只改提示词形态：

- **A 组（随机 token）**：用随机 token id 解码成文本，等价于官方客户端 random 数据集的构造；
- **B 组（自然散文）**：等长（16384 token）的普通英文散文。

两组都用 `ignore_eos=True`、`max_tokens=1024`，因此输出长度**受控一致**；
差异只可能来自「文本本身被压缩的程度」。

| 组别 | 提示词文本 token | 引擎生成 token（usage） | 文本重新分词长度 | 比值 | 40-gram 重复率 | 文本字符数 | 耗时 s |
|---|---|---|---|---|---|---|---|
| gibberish_random_tokens | 17192 | 1024 | 978 | 0.955 | 57.3% | 4989 | 53.5 |
| natural_prose | 16384 | 1024 | 992 | 0.969 | 0.0% | 4929 | 43.6 |

**结论**：

- A 组（随机提示词）：引擎生成 1024 token，但同一段文本重新分词只要 978 token（比值 0.955），
  40-gram 重复率 **57.3%** —— 模型面对随机提示词时输出了高度重复的内容，
  重复文本被 BPE 压成更少的 token，因此 `total_output_tokens_retokenized` 偏小。
- B 组（自然提示词）：引擎生成 1024 token，重新分词 992 token（比值 0.969），重复率 0.0% —— 
  **同样存在压缩**（比值 < 1），只是重复率为 0，压缩幅度明显更小。
- **A 组比 B 组多压缩 1.4 个百分点**（A 组压缩 4.5%，B 组压缩 3.1%）。
  这个差值**只能解释官方压测中重分词偏差的一小部分**（官方 16384/并发 64 档偏差约 22.6%）：本次对照是**单请求、1024 token 输出**，而官方那一档是 128 个请求、运行 2 小时、每请求的退化程度远高于本对照的平均水平。
- **因此要说清楚**：本对照**证明的是方向**（随机 token 提示词 → 输出退化 → 重分词更短，**与提前 EOS / 生成变短无关**），**不是官方那一档 22.6% 偏差的完整定量归因**。
  决定性的证据仍然是 §3.7 的**服务端引擎计数器交叉核算**（引擎生成量 = 计划量的 95.6%–99.7%，决定性一档 99.7%）；官方 `output_throughput` 列（引擎生成速率）**可直接填报**。

> 对「16384 输入档的重分词偏差（12%–23%）比 4096 档（≤7%）大」的解释（上下文越长、随机 token 越密集，模型越容易滑入重复输出）目前是**与数据一致的推断**，不是本对照直接证明的结论 —— 本对照未覆盖不同输入长度。

**证据**：`outputs/phase5_token_accounting/result.json`（含完整生成文本的头尾片段）。
