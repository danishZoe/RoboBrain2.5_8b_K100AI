## 1. 结论

**精度项目前无法与官方基线比较，状态是 `BLOCKED`，既不能宣称达标也不能宣称不达标。**
**性能项目前没有"外部官方基线"可比——官方口径就是"首次提交的性能实测即该件基线"。**

已完成的是 **A 阶段（目标设备跑通）**、**B 阶段（功能与服务通过）**、
**C 阶段的性能部分（六档两轮压测 + 干净环境复现）**：
指定框架 **vLLM serving 已跑通**，四类任务、单图/多图、流式、多轮、异常输入均有服务级证据，
且定位并修复了一个此前被误判的数值根因（图像二次重采样）；
六档压测两轮共 480 个请求零失败，输出 token 计量口径已用服务端引擎计数器定量闭环。

**当前处于验收标准的 B 级 + 性能件就绪**；C 阶段精度项因缺官方材料仍为 `BLOCKED`，
D 阶段（优化 ≥10%）因 §8.2 的第二个条件依赖精度复验，同样**无法判为通过**（见 §6 风险 #13）。
提交配置保持首提基线，非 eager 与 token 预算两项候选优化的收益与代价如实登记，不宣称达标。

## 4. 我们能自证的数值稳定性（目前唯一可量化的"差距"）

固定样例（官方 6 张 demo 图 + 官方提示词）、贪心解码、单卡同一进程内受控对比：

| 对比项 | 结果 | 归一化坐标偏差 | 判定 |
|---|---|---|---|
| 同配置重复 3 次 × 6 样例 | **6/6 逐字符相同** | 0% | 自一致 ✅ |
| `attn_fa2` vs 基线 SDPA | 6/6 格式一致；trajectory 第 2 点 `(405,350)`→`(400,350)` | ≤0.5% | 可接受，已回退 FA2 |
| `pix_501760`（采纳）vs 基线 | 5/6 完全相同；navigation `(400,376)`→`(406,378)` | **≤0.6%** | **采纳** |
| `pix_200704` | grounding bbox `[0,309,620,989]`→`[51,300,411,520]` | **~48%** | **拒绝** |
| 批处理 bs=4 vs bs=1 | 26 次比对 10 次不完全相同（general 自由文本尾部措辞、affordance 坐标微移） | 坐标级 ≤1% | 采纳（已目视复核目标不变） |
| **取图路径：原图上传 vs 官方 `qwen_vl_utils` 规范化** | grounding 从**不可解析**变为 `[0,309,620,989]`（与基线**完全一致**）；pointing 5→0；navigation 4→1；trajectory 25→7 | **7/1000 = 0.7%** | **采纳规范化**（见 `09` §3–§4） |

**判读（必须讲清楚的边界）**：我们证明的是「**本机实现对配置扰动是稳的，漂移 ≤1%，小于官方 2% 容差带**」，
这说明留出了 2% 劣化里的余量；但它**不等于**「与官方 GPU 基线一致」——
后者必须用官方 GPU 参考输出做逐项比对，我们手上没有这份材料。

**本轮新增的一条重要结论**：**扰动源不只是「数值扰动」，还包括「输入预处理路径」**。
官方 upstream 的 `qwen_vl_utils` 会对图像做一次 28 倍数缩放，processor 再做一次 32 倍数缩放（**二次重采样**）；
serving 若直接上传原图只经历一次缩放，像素最大差 **0.47**（归一化 ±1 空间），
足以翻转 grounding 首个生成 token（`The`/`To` 在 bf16 下 logit 完全相等 24.5）。
→ 提交形态必须包含「客户端图像规范化」这一步，否则官方判分会把正常输出判为不可解析。

## 6. 口径风险（提交前必须处理，否则会被评审挑）

1. **官方 `env.sh` 默认 `TP=4`**，我们只有 1 卡 → 性能基线是**单卡口径**。
   若官方基线在 4 卡下测得，「同负载」不成立，需在报告第 4/6 节显式标注卡数口径。
2. **样例量 6 条**：足够做同口径回归对比，不足以代表官方题集分布，
   不能用来声称任何精度结论。
3. **transformers 直跑 ≠ serving**：验收标准 §1.3 明确「Transformers 直跑属于 A 阶段和诊断基线，
   不能替代 T02 的 SGLang/vLLM serving 适配；只用 HTTP 包装 Transformers 也不能声明完成指定框架适配」。
   → 本报告第 5.2 节才是提交口径，第 5.1 节只作历史对照。
4. **首提基线只有一次机会**：性能基线 = 首次提交的性能实测，所以 serving 打通后**第一次**压测
   的口径（卡数、并发、输入长度、图像尺寸、max_tokens）必须一次定死并写进 `env.sh`。
5. **图像处理方式会改答案**：`max_pixels` 从 501760 降到 200704 使 grounding bbox 改变 48%；
   **取图路径**（原图 vs 官方 `qwen_vl_utils` 二次重采样）使 grounding 从不可解析变为完全一致（差异 100%）。
   → 两项都必须冻结：**图像规范化 + 分辨率预算**。官方题集图像尺寸分布未知，
   拿到官方图集后仍需**先重跑一次 `max_pixels` 敏感性**再冻结配置。
6. **prefix caching 会污染压测**：本轮实测到 vLLM 默认开启 prefix caching 时命中率 **64%**，
   相同 prompt 的 prefill 成本几乎被抹掉。压测口径已改为 `--no-enable-prefix-caching`
   且每个请求使用不同 filler 文本（token 数相同）。
7. **KV cache 容量限制并发度**：253,312 token 的 KV 意味着
   16384 输入 + 1024 输出档在并发 64 时**实际并发约 13**（`253312/19448`，其中 19,448 = 文本 ~16,382
   + 视觉 2,042 + 输出 1,024）。该档结果必须标注真实并发度，不能按请求的 64 并发宣称。
8. **上下文容量必须覆盖「文本 + 视觉 + 输出」**：早期把 `MAX_LEN` 设成 20480，
   而 16384 档单请求实际需要 ≈20,336 token（随机文本解码后重编码膨胀 ~5.4%），
   超出的请求被直接拒收 → 该档根本跑不完。已改回官方 `env.sh` 的 **32768**；
   实测该改动**不改变 KV cache 容量**（两种取值均为 253,312 token），因此不影响性能可比性。
9. **压测客户端的输出计量有坑（已定性并闭环）**：官方客户端 `total_output_tokens` 统计的是**计划长度**
   （`output_lens.append(output_len)`），不是实际生成量；只有 `total_output_tokens_retokenized`
   暴露真实长度。且 `--disable-ignore-eos` 的语义是**允许提前 EOS**（与直觉相反），
   官方脚本不传该开关即为 `ignore_eos=True`。此前误加该开关导致吞吐虚高约 4×，
   且**从 `total_output_tokens` 完全看不出来**。
   **闭环结论**：已用 vLLM 引擎自己的计数器独立核算全部 11 个已完成档位 ——
   引擎实际生成量是计划量的 **95.6%–99.7%**（决定性一档 16384/并发 64 达 **99.7%**，
   130,616 vs 131,072），引擎吞吐与官方表吞吐列偏差仅 **−0.2%**，
   **确认不存在提前 EOS，官方 `output_throughput` 列可直接填报**；
   `total_output_tokens_retokenized` 偏小是**文本压缩**（随机提示词导致输出退化），
   详见 `reports/10_phase5_bench.md` §3.7 / §3.8 与 `reports/11_tuning_experiments.md` §5。
   → 该风险从「未定性」转为「已定量定性」，提交前无需再纠结口径。
10. **`verify.py` 的「基线存在」分支曾是空壳**：它只把基线文件里的数值抄进结果并置
    `passed=true`，**根本没有调用服务**。官方材料一旦下发，就会产出一个没有证据的 PASS
    （触及赛事红线「伪造日志 → 取消资格」）。现已重写为真正跑评测：
    缺子集/参考输出/判分器 → 该指标 `BLOCKED`、整体不判 PASS、退出码 2；
    只有全部指标都真的跑完才可能 PASS。已用合成基线做过三项路径验证
    （selfcheck / 缺基线 / 缺子集），合成件用完即删，仓库里不留任何自建基线。
11. **单卡口径下的并发 64 档不能按请求并发解读**：KV cache 只有 253,312 token，
    4096 档单请求占 7,374 token（实测服务侧常驻 50 路），16384 档单请求占 ~20,316 token
    （实测常驻 15 路，p50=15 / p90=16）。该档 TTFT 反映**排队**而非模型变慢；
    与官方 TP=4 基线比较时必须同时给出卡数与实际并发度。
12. **长任务链路的超时预算必须覆盖最坏单任务耗时**（2026-10-27 18:20 实测拦下的隐患）：
    收尾流水线的「等待压测结束」环节原设定为**启动时刻 + 4 h**，而最后一档
    （16384/并发 64）单轮就要 ~2.2 h、六档两轮合计远超 4 h → 截止时刻会**早于**压测结束，
    流水线会带着 5 档数据提前进入 E1/E2；而 E2/E3 的 A/B 脚本会 `pkill` 服务进程，
    **会直接杀掉正在被压测的服务器**，最后一档数据作废。
    修正：① 等待条件改为「压测进程退出 **且** `round2.jsonl` 已有 6 条」；
    ② 超时预算改为 10 h，且超时后**直接退出**而不是带着半个结果继续；
    ③ 给 E2/E3 也加了与 E1 相同的「压测在跑就拒绝启动」安全闸；
    ④ 第二段流水线与干净复现脚本同样加了「压测未结束就不发任何请求 / 不重启服务」的闸。
    —— 这条属于流程性风险，与模型无关，但一旦发生会**静默毁掉整轮数据**。
13. **验收标准 §8.2 的「优化提升 ≥10%」在本节点无法判为通过**（2026-10-27 实测后登记）：
    §8.2 有两个条件 —— ① 同卡型、同框架、同负载下提升 ≥10%；② **优化后必须重跑官方精度门槛，
    精度未通过的性能结果不算优化验收成功**。
    E1（非 eager）是本节点唯一达到 ① 的候选：4096/并发 1 档输出吞吐 **+30.5%**（TPOT −23.8%），
    但官方口径核心的并发 8 档只有 **+0.2%**（落在同档两轮实测波动 <2.3% 内），
    并发 64 档非 eager 未测量 → **不构成整件级 ≥10%**；
    且非 eager 下输出数值发生变化（与 transformers 基线逐坐标一致率 3/6 → 2/6，
    最大坐标偏差 7/1000 → 30/1000），而条件 ② 要求的官方 ≥98% 一致率因缺官方 GPU 基线
    **无法验证该变化无害** → 条件 ② 不成立。
    处置：提交配置**保持首提基线**（`--enforce-eager`），非 eager 的可启动性与收益/代价如实写入
    `reports/11_tuning_experiments.md` §2 与 `reports/05_final.md` §4.6；
    **不宣称性能优化达标**，也不把单档 +30.5% 写成整件提升。
